# AI 工作空间目录应用模板

本模板用于规划一个包含 `platform`、`skills`、`automations`、`experiments` 和 `documents` 的 AI 工作空间。内容应保持可复用、可运行、可审计，不得放入密钥、凭证、个人数据、客户数据或公司敏感资料。

## 目录与实际应用

### `.github/workflows`

用于自动检查、发布和定时任务。

- 自动运行测试、格式检查和类型检查
- 执行依赖或安全扫描
- 构建并部署 `platform` 项目
- 定时运行数据质量检查
- 在工作流失败时生成可追踪的诊断信息

### `archive`

用于保存已退出使用但仍有参考价值的内容。

- 旧版分析工具和历史报表
- 废弃实验和旧工作流
- 迁移前代码与变更说明
- 按年份和项目名归档，例如 `archive/2026/project-name`

归档内容不应继续作为生产流程的默认入口。

### `automations`

用于无人值守或定时执行的脚本和工作流。

- 每日数据质量检查
- 每周业务报告生成
- 监控输入文件夹并触发分析
- 发现异常指标后发送通知
- 定期下载、整理或汇总授权数据

每个自动化建议包含独立的配置示例、运行入口、失败处理方式和权限说明。

### `documents`

用于保存业务和技术文档，以及可复制的模板。

- 数据字典和字段定义
- 指标口径和计算规则
- 产品需求和使用场景
- 操作手册和故障排查指南
- 分析报告、会议结论和架构说明

推荐结构：

```text
documents/
├── guides/
├── templates/
│   └── workspace-application-scenarios.md
├── data-dictionary.md
└── README.md
```

### `experiments`

用于验证想法、方法和模型，不直接承担正式生产流程。

- Jupyter 数据分析 Notebook
- 透视表和多选维度分析实验
- 缺失值处理策略对比
- 异常检测和指标预警实验
- 图表推荐和提示词评估
- SQL 或数据处理性能测试

实验应记录目标、输入、方法、结果、限制和下一步。验证有效后，再将成熟逻辑迁移到 `platform`、`skills` 或 `automations`。

### `platform`

用于面向用户的正式应用和可交付产品。

适合的首批功能包括：

- CSV/Excel 上传和字段类型识别
- 缺失值、重复值和异常值检查
- 透视表字段拖放和多选维度分析
- 图表预览和筛选器
- 分析结果导出
- 最近处理记录和运行状态

正式应用应有清晰的启动方式、验证命令、错误提示和数据边界说明。

### `skills`

用于封装 Codex 可以重复执行的工作流程。

可优先建立以下 Skill：

- `data-profile`：识别数据结构和质量问题
- `pivot-analysis`：根据业务问题生成透视分析
- `report-generator`：生成结构化业务报告
- `data-reconciliation`：执行名单或数据对账
- `data-cleaning`：执行可审计的数据清洗
- `chart-advisor`：根据字段和问题推荐图表

每个 Skill 建议包含：

```text
skills/<skill-name>/
├── SKILL.md
├── scripts/
├── references/
├── templates/
└── examples/
```

## 推荐的贯通场景

优先实现以下三个真实场景：

1. 数据质量检查：在 `experiments` 中验证规则，在 `skills` 中固化流程，在 `automations` 中定时执行，在 `platform` 中展示结果。
2. 透视分析：在 `platform` 中提供字段配置和多选分析，在 `documents` 中记录指标口径，在 `skills` 中提供可复用分析步骤。
3. 自动周报：从授权数据源读取数据，执行质量检查和汇总，生成报告并通过已授权渠道通知相关人员。

## 目录边界

| 目录 | 核心问题 |
|---|---|
| `experiments` | 这个方法是否有效？ |
| `skills` | 以后如何重复执行？ |
| `automations` | 什么时候自动执行？ |
| `platform` | 用户如何实际操作？ |
| `documents` | 为什么这样做、口径是什么？ |
| `archive` | 已退出使用的内容如何保留？ |

## 发布前检查

- 确认内容不包含密钥、凭证、个人数据或客户数据
- 确认示例数据已经脱敏或使用合成数据
- 确认文档中的命令、路径和入口与实际项目一致
- 运行目标项目规定的测试或构建命令
- 执行 `git diff --check`
- 在变更记录中说明目标路径、摘要和验证结果
